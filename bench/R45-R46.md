## Node param A/B investigation (2026-09-04, v1.0.0 vs the lifecycle line)

The R4.5-vs-HEAD A/B shows Node param at 0.95x (12-round interleaved,
reproduced twice). Bisect ladder: R4.5 ≈78.7–80.8k, lifecycle tip bd54826
≈80.4k, merge point 81dbce3 ≈75.3k, HEAD ≈75.8–77.0k — the drop lands at
the integration merge, not in any single workstream commit.
Counter-evidence narrowing it to a second-order effect: the in-process JS
chain is FASTER on HEAD (handle() 872ns vs 907ns on the R4.5 worktree);
transport instrumentation shows zero headers()/request()/header()
materializations on the param path; the request-closure hot path is
textually equivalent between trees; a client-in-process profile ties
(67.2k vs 67.4k). The delta emerges only under the harness's
external-4-worker shape. Bun param is unaffected (HEAD +1.3%).
Official-matrix node-param K/H stays inside its historic band.
Open lead: merged-tree × external-worker interaction (code layout / IC
effects in the server process). Not blocking GA; revisit if a future
window reproduces it against Hono as well.

## Follow-up (same day): the Node param delta is a JIT inlining cascade, not an algorithmic regression

Chased with per-frame CPU profiles under the exact harness shape (4
external autocannon workers, self-exiting fixture so --cpu-prof flushes —
SIGKILL/SIGTERM never flush):

- File-level aggregation: router.ts is the ONLY significant mover — HEAD
  3.7% self-CPU vs lifecycle 0.87%. Everything else is noise.
- Controls that do NOT explain it: reverting the R4.8 registration guard
  (3.65%), removing the r4-7 /search route (3.50%), constructor-only
  fixture change (0.67%), imports-only change (0.88%), swapping the FULL
  HEAD fixture into the lifecycle tree flips it to 3.60% — the delta
  follows a fixture/src interaction, not any single change.
- Caller analysis: both trees call fastMatch from the identical
  matchRoute; HEAD burns ~8x more self-time in it (550 vs 70 samples)
  with byte-identical router code and equivalent route tables. The
  in-process handle() chain is FASTER on HEAD (872ns vs 907ns) — the JS
  work per request did not get algorithmically slower; it stopped
  inlining as deeply (the R4.7/R4.8 dispatch.ts/app.ts shape changed the
  optimization cascade around matchRoute).
- Magnitude check: +2.5pp router CPU ≈ the observed −3~5% Node param
  RPS. Bun (JSC) is unaffected (HEAD slightly faster).

Disposition: documented, not blocking. If a future release wants the
last ~4% back on Node param, the lever is recovering matchRoute inlining
(e.g. by slimming the dispatch call shape around it), verifiable with
this same profile harness. The official matrices (keala vs hono) are
unaffected — both frameworks pay their own matching cost in every leg.
