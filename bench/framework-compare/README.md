# Keala / Hono / H3：Node 26 与 Bun 1.4.4

当前 Node 请求路径重构、冻结基线同机 A/B、源码与验证证据见
[本轮结果索引](node-architecture-2026-11-01/README.md)。

前一版本 `f14940b` 在 `ssh wr` 的共享 Linux 服务器完成测试：
[完整服务器结果](wr-2026-11-01/REPORT.md)、[远端测试与清理协议](REMOTE.md)。
该轮为 50 连接、单负载进程、整个测试合计最多 1.5 核 / 640 MiB；
不能与下面不同机器和参数的本地历史结果直接换算性能变化。

已保存的实测使用 200 连接、每次 3 秒、3 轮、4 个客户端进程：
[完整结果](REPORT.md)，[每轮原始数据](results.json)。
首轮因计时校验中止的数据单独保存在 `interrupted-results.json`，不参与正式汇总。

```bash
bun install --frozen-lockfile
npm run bench:compare -- 200 5 3 4
```

参数依次为总连接数、每次测量秒数、轮数、客户端进程数。以上也是默认值。
需要真实 Node 26 和 Bun 1.4.4；可通过 `BENCH_BUN` 指定 Bun 路径。
执行前自动构建当前工作区的 Keala，Hono 与 H3 版本由锁文件固定。

只检查正确性、不压测：

```bash
npm run bench:compare -- --verify-only
```

完整矩阵包含 3 个框架 × 2 个运行时 × 13 个场景：

- **Hello World**：独立应用只注册 `GET /`，正文为 `Hello World`。
- **十二路由**：应用注册用户指定的完整十二路由表，每条路由独立测量；
  请求路径和期望响应见 `scenarios.mjs`，参数必须读取并回显。
  POST 无请求体，通配路径回显后缀，不读取磁盘文件。

每组应用六个服务常驻，仅对一个服务加压；每场景每轮轮换顺序，
奇数索引轮反转次序。每次测量用四个独立 Node 进程生成负载，
连接数在进程间准确分配；各客户端预热 1 秒后同步开始测量。
所有服务均为单进程、生产模式、默认框架适配器、无额外中间件。
Keala 不使用 `direct`、`nativeStatic` 或预建 Response。

压测前逐项检查状态码、Content-Type 和正文，还检查不同参数、
多段通配、404 和错误方法；Hello World 与十二路由合计 132 项 HTTP 检查。
压测期间每个请求检查正文，错误、超时、非 2xx 或不匹配会中止测试。
对墙钟与单调时钟不一致、客户端启动时间差超限这两类无效计时，
记录拒绝原因并重新预热、重新采样，每组最多尝试三次；有效的慢样本仍保留。
复用 `bench/load-pool.ts` 合并客户端延迟直方图，并记录客户端 CPU；
任一客户端 CPU 达到单核 90% 的样本会标记受限。

完成后写入本目录的 `REPORT.md` 和 `results.json`，后者每次采样后更新。
可通过 `BENCH_OUTPUT=/absolute/path` 改变输出目录以保留多次测试。
报告使用每场景吞吐量的轮间中位数，保留各轮范围与 p50/p99。
十二路由汇总为十二个中位数的几何平均，**并非混合请求吞吐量**。

结果取决于测试机器、系统负载和客户端能力。客户端与服务端共用本机，
因此用于同一环境下比较，不能直接推算生产容量。JSON 记录精确版本、
Git HEAD、未提交文件列表和构建产物摘要；结论对应该工作区快照。

H3 的部署入口使用官方 [`serve`](https://h3.dev/guide)，
多段通配使用官方 [`/**` 语法](https://h3.dev/guide/basics/routing)。
