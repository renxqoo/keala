# Bun CPU 与 Node p99 因果诊断

本轮确认了 Bun 原始 Request 扩展安装路径的显著端到端成本；没有复现此前 Node POST 的稳定 p99 退化。两种保留兼容行为的试改没有证明跨场景收益，均未进入产品。当前产品源码仍为 Xi：`33f23a18be16853fdaa06371aee662a1138723e229b0e9fac06d02c0b82b2067`。全面领先尚未达成。

## 方法与校准

在 wr 直接运行本地构建，Node 26.9.0、Bun 1.4.4，无 Docker、无系统包安装。仅测试 cgroup 使用总 CPU 150%、MemoryHigh 512MiB/Max 640MiB、swap 0、nice 15；服务端 CPU 0、原生 Go 客户端和协调进程 CPU 1。沿用 50 连接、预热 1 秒、计量 3 秒、500ms 间隔及逐请求状态/正文检查。

旧顺序只覆盖部分起始位置。新 `balancedOrder` 遍历全部起始位，每个紧邻一个精确反向轮次。A/A 使用 8 栈 × 16 轮，两个 Keala 标签加载相同入口 URL、相同源码和构建。Bun 对照用 12 轮；Node 周期对照用 6 栈 × 12 轮。每个样本记录实际 `cpu.max` 和 Keala 入口，finally 恢复并读回配额。

分析采用同轮配对差值；探索性 bootstrap 以相邻反向两轮为块，固定种子、重采样 10,000 次。区间不能涵盖共享主机状态漂移等系统性不确定性。延迟仍是向下取整的整数毫秒桶。本轮局部诊断不能替代完整十三场景的版本排名。

相同构建的 A/A CPU 配对中位差：Node −4.94%，区间约 [−9.11%, +0.93%]；Bun −0.21%，区间 [−1.87%, +1.19%]。两者均包含零。小幅差距不能直接认定来自代码。

## Bun：安装扩展路径的消减效应

临时副本只去掉 `waitUntil/runtime/ip` 的安装，其余源码与依赖相同。它改变原始 Request 的公开行为，仅作为诊断，不能进入产品或作为兼容版本成绩。

| 场景          | CPU/请求配对变化 | CPU 绝对变化 | CPU 下降轮数/12 | 吞吐配对变化 |
| ------------- | ---------------: | -----------: | --------------: | -----------: |
| Hello         |           −9.93% |      −3.27µs |              12 |      +11.30% |
| user/comments |           −7.20% |      −2.43µs |              12 |       +7.31% |
| static/*      |           −6.21% |      −2.30µs |              11 |       +5.77% |

这是整段代码及其连带影响的端到端效应，包括对象形状、分配和编译状态；没有单独证明某次 `defineProperty` 的成本或具体 JIT 原因。该开销比上轮 Bun 对 Hono 的平均 CPU 差距更大，支持继续聚焦兼容扩展层，但不能直接删除现有行为。

## Node：先前 POST p99 落后未复现

旧三轮中，另外三个 p99 落后项目已经存在轮间反向；POST 才是三轮均落后。本轮用同入口 A/A 加 Hono、完整平衡顺序重复 POST：

| 调度配置/对照         | p99 配对差中位数 |    探索性区间 |
| --------------------- | ---------------: | ------------: |
| 10ms 周期，Keala−Hono |           −5.5ms |   [−13, −2]ms |
| 1ms 周期，Keala−Hono  |           −6.5ms |    [−9, −4]ms |
| Keala，1ms−10ms       |          +10.5ms | [+5, +11.5]ms |
| Hono，1ms−10ms        |             +6ms |   [+4, +12]ms |

1ms 并未改善尾延迟：Keala 吞吐配对中位下降约 21.95%、CPU/请求增加 14.31%；Hono 下降约 18.23%/增加 9.51%。总 CPU 上限仍为 150%，原配置保持 10ms。这个干预证明调度参数会显著影响结果，没有证明它是旧三轮差异的唯一原因，也没有找到需要修复的稳定 Node POST p99 退化。

## 兼容方案裁决

| 方案                          | Hello CPU | comments CPU | wildcard CPU | 裁决                                     |
| ----------------------------- | --------: | -----------: | -----------: | ---------------------------------------- |
| 批量 defineProperties         |    +7.58% |       +5.69% |       +4.69% | 未观察到收益，不采用                     |
| 提取同步 extendRequest helper |    +1.58% |       −0.77% |       +2.15% | CPU 区间均含零，未证明跨场景收益，不采用 |

批量方案完整保留了描述符和重入保护，通过公开行为探针及只读审查。函数提取保持原三次定义顺序，通过 17 项既有 Bun 契约和只读审查。没有通过改变有效断言保留试改。

批量实验中，基线与候选同时出现数量级变慢的区段，后来恢复；所有慢样本完整保留。该波动根因没有确定，不能只据此认定精确退化幅度。结果无稳定收益已足以拒绝作为优化；本轮没有对生产源码应用该方案。
