# wr 服务器：受限资源测试

**因果诊断数据，不作为兼容产品版本排名。**
试验：Compatible extraction of eager extension installer, same three defineProperty calls and order, isolated candidate vs Xi；对照类型：packaged-before。

本次在服务器直接运行本地编译的 Keala，无 Docker。仅监听 127.0.0.1，每次一个服务进程、一个负载进程；每次采样重启服务。
整个测试 cgroup（包含服务端、客户端、协调进程）CPU 上限 1.5 核、内存 640 MiB、任务数 128；nice=15，CPUWeight=1。
这是共享服务器上的资源受限比较，吞吐和延迟包含 CPU 配额与负载端竞争的影响，不能作为服务端峰值容量。客户端低于 90% 也不排除配额限制。与本地旧结果的参数、机器不同，不能直接计算前后变化。
服务端 CPU/请求取 process.cpuUsage(user+system) 增量除以完成请求数；通过 HTTP 路径外的 IPC 采样，窗口包括负载启动屏障及结束清理。延迟分位数精度为毫秒。

失败：无；退出后仍存活的测试子进程：0。

# Node 26 / Bun 1.4.4：Keala、Hono、H3 实测

- 测试时间：2026-11-01 22:17:41 → 2026-11-01 22:23:18（Asia/Singapore，UTC+8）。
- 机器：Intel(R) Xeon(R) CPU E5-2680 v4 @ 2.40GHz，2 逻辑 CPU，2 GiB，linux 6.8.0-48-generic x64。
- 版本：Node 26.9.0、Bun 1.4.4；Keala 0.7.3（工作区构建）、Hono 4.13.5、H3 2.0.8；@hono/node-server 2.1.1、srvx 1.0.8。
- 负载：原生 Go 客户端 go1.27.0，50 个总连接，1 个独立客户端进程，HTTP/1.1 keep-alive，pipelining=1。
- 原生客户端复用预热连接，逐请求校验状态与完整正文；到计量截止时停止新请求，最后在途请求排空的完成数及时间均计入实际分母。不能与旧 autocannon 数据直接换算性能变化。
- 仅测试进程固定 CPU：服务端 0，负载与协调进程 1；原服务未调整。
- 每次采样先预热 1 秒，再测 3 秒；12 轮，交错并轮换顺序。表格为轮间中位数，范围为实测 min–max，不代表置信区间。
- Hello World 应用仅注册 GET /；十二路由应用注册完整路由表，每次固定请求其中一条。所有响应状态为 200、语义相同的 text/plain UTF-8，正文逐字节一致；每个压测请求也检查正文。
- 参数必须实际读取并回显；POST 无请求体；/static/* 仅回显后缀，无文件 I/O。H3 用 /static/** 实现多段通配契约。
- Keala 使用默认原生适配器（Bun 为 app.listen，Node 为 keala/node）；Hono 使用 Bun.serve / 官方 Node 适配器；H3 使用官方 serve（srvx）。均为生产模式、单进程服务，无额外中间件。
- 客户端和服务端共用本机；其他系统活动、网络栈和客户端均可能影响结果。客户端任一进程 CPU ≥90% 单核的样本会标记，不能直接解释为服务端极限。
- 主机一分钟负载（测量前后采样）范围：0.37–2.22；若接近或超过逻辑 CPU 数，需注意竞争负载与调度影响。
- 严格计时校验未通过的样本共 0 次，记录原因后重新预热、重新测量，单组合最多尝试 3 次。正文、状态、超时等失败不重试；有效的低吞吐样本不会被删除。
