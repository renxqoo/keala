# Kernel 当前源码 HTTP 复测

默认 trie Kernel 相对当前 Keala 的十二路由综合表现接近持平，尚不足以支持为性能迁移整个框架。显式 RegExp 方案在这批小路由表、同步文本场景中有小幅平均收益，Bun 六轮的方向尤其一致。此次保留实验入口和默认配置。

旧版 R4.5/R4.6 专用对比脚本和报告已清理，迁移历史保留在[生命周期记录](../../../docs/HOTPATH-R4-6-MIGRATION-LIFECYCLE.md)。本报告比较同一源码快照中的 Keala 与实验 Kernel。

## 观测结果

相对 Keala，吞吐为正表示更快，CPU 为负表示每请求 CPU 更少。每场景取六次测量的中位数，十二路由再取几何平均；它不是混合流量吞吐。

| 运行时 / 候选    | Hello 吞吐变化 | Hello CPU/请求变化 | 十二路由吞吐变化 | 十二路由 CPU/请求变化 |
| ---------------- | -------------: | -----------------: | ---------------: | --------------------: |
| Node / 默认 trie |         +5.39% |             −5.10% |           +0.68% |                −0.75% |
| Node / RegExp    |         +1.77% |             −1.31% |           +3.82% |                −4.02% |
| Bun / 默认 trie  |         +5.54% |             −5.59% |           +0.80% |                −0.10% |
| Bun / RegExp     |         +4.87% |             −4.85% |           +5.52% |                −5.89% |

| 运行时 / 实现    | Hello req/s | Hello CPU µs/请求 | 十二路由 req/s 几何平均 | 十二路由 CPU µs/请求几何平均 |
| ---------------- | ----------: | ----------------: | ----------------------: | ---------------------------: |
| Node / Keala     |    8,922.51 |            103.70 |                8,068.90 |                       115.69 |
| Node / 默认 trie |    9,403.87 |             98.41 |                8,123.46 |                       114.83 |
| Node / RegExp    |    9,080.73 |            102.34 |                8,377.43 |                       111.05 |
| Bun / Keala      |   20,467.28 |             36.31 |               19,690.41 |                        38.88 |
| Bun / 默认 trie  |   21,600.47 |             34.28 |               19,847.16 |                        38.84 |
| Bun / RegExp     |   21,463.26 |             34.55 |               20,776.38 |                        36.59 |

默认 trie 的六轮配对十二路由几何平均相对 Keala 多次改变方向，Node 吞吐范围 −10.33% 至 +1.53%，Bun 为 −2.50% 至 +3.86%。Hello 的约 5% 收益不能代表动态路由或完整应用。

RegExp 在 Node 六轮中五轮提高十二路由平均吞吐、六轮降低平均 CPU；Bun 六轮全部提高平均吞吐、降低平均 CPU。Bun 配对结果如下，它与“每路由先取中位数”的主表是两种不同汇总：

| 轮次 | 十二路由吞吐变化 | 十二路由 CPU/请求变化 |
| ---- | ---------------: | --------------------: |
| 1    |           +6.12% |                −6.31% |
| 2    |           +6.43% |                −6.85% |
| 3    |           +5.56% |                −5.40% |
| 4    |           +3.81% |                −3.82% |
| 5    |           +5.98% |                −5.96% |
| 6    |           +5.12% |                −6.15% |

同一 Kernel API 内，RegExp 相对 trie 的十二路由吞吐在 Node/Bun 分别高 3.13%/4.68%，CPU 分别低 3.29%/5.79%；七条动态路由的吞吐高 5.22%/7.83%，五条静态路由仅高 0.26%/0.43%。收益主要与动态匹配方向一致；本实验不能将整个 Kernel/Keala 差值单独归因于路由算法。

尾延迟没有全面改善。Bun RegExp 在十二路由中只有八条的 p99 中位数严格更低，`route-7`、`route-8` 稍高；Hello 的 trie/RegExp/Keala p99 分别为 11.5/10/10.5 ms。[Node 统计](node/analysis.json)和[Bun 统计](bun/analysis.json)保留全部逐场景中位数、范围和对比。

## 样本与边界

- 测量源码为 `e8600d2bb7d377affea9adf6728e9404991a5e70`。打包时工作区已有本次文档与旧脚本清理，完整清单保留在 [manifest](manifest.json)；产品和 Kernel 源码未修改。产品源码 SHA256 为 `b04ef67fa78d11a30b17dec0e8cc99fdb0e167a6c7554220c950c6a901061751`，Kernel 为 `60d94ea18d0d6764ba7e652ace40143bcfbbec273093442407aecd21e6f1e36d`。
- Ubuntu 24.04.5 x86_64，共享的 2 vCPU、约 2 GiB 主机；Linux Node 26.9.0、Bun 1.4.4。Node 来自官方同版本发行归档，执行前核对本地取得的官方 SHA256，未安装系统软件包。[运行时来源](runtime-provenance.json)记录校验值。
- 沿用现有 `remote-run.mjs`、场景、HTTP 服务和原生 Go 客户端，不更改被测实现。Go 工具链本地不可用，因此复用已归档的 Linux 二进制，核对其二进制和当前 Go 源码摘要；没有声称重新编译或测试 Go 源码。
- `kernel`、`kernel-regexp`、`keala` 各测 Hello 和全部十二条既有路由。Node、Bun 分开串行运行，各六轮、234 份样本；三种实现轮换起始位置并覆盖反向顺序。每份样本新建服务，50 连接、预热 1 秒、计量 3 秒、冷却 500 ms。试跑另有六份 Hello 样本，不参与排名。
- 服务固定 CPU 0，负载和协调进程固定 CPU 1；它们共享 1.5 核 cgroup 配额。每个计量窗口实际 `cpu.max=15000 10000`，完成后恢复 `150000 100000`；systemd 静态属性中的 100 ms 周期不代表计量周期。内存上限 640 MiB，任务数上限 128，完整限额见各运行时的 `limits.txt` 与[远端流程](../REMOTE.md)。
- 每次计量只有一个服务和一个负载进程，服务仅监听回环地址的临时端口。CPU 使用 HTTP 外 IPC 记录的服务进程 user + system 增量，除以完成请求数；窗口包括负载启动屏障和客户端结束清理。客户端逐请求验证 200 和完整响应正文，参数路由读取真实参数，处理器逐请求执行。
- 所有场景都是小路由表的显式同步 `.text()` 路径，没有中间件、JSON/body、异步任务或文件 I/O 性能测量。普通 Kernel 的 Fetch/中间件等能力另有行为测试；本轮没有证明其通用能力与 Keala 公共 API 等价。
- 本轮没有运行 uWS、Hono 或 H3 对照。历史约三倍数字来自 `kernel-uws` 同步文本执行器探针，它缺少通用 Fetch、中间件、异步结果和有期限关闭，不能套用于普通 Kernel 或完整框架。历史数据见[独立实验归档](../kernel-2026-11-01/)。

这是共享主机、客户端共机、短测量窗口下的描述性结果，尚未建立生产负载的置信区间或持续收益。各组中位节流时间 Node 596–625 ms、Bun 814–843 ms，均发生在约 3 秒的窗口；客户端虽未被工具标记为容量受限，吞吐和延迟仍不能解释为服务端峰值。毫秒级 p99 也有量化影响。

有效慢样本全部保留：例如 Node trie `route-3` 第二轮只有约 3,270 req/s，其余轮为约 7,962–9,032 req/s，该样本没有错误，未重试或排除；具体变慢原因未经证明。Bun RegExp 通配路由也保留 16,697–21,318 req/s 的完整波动范围。平均改善不意味着每路由、每轮或尾延迟都更优。

## 复算与复测

在仓库根目录复算保存的统计：

```sh
node bench/framework-compare/kernel-2026-11-01/analyze.mjs bench/framework-compare/kernel-recheck-2026-11-02/node/results.json.gz
node bench/framework-compare/kernel-2026-11-01/analyze.mjs bench/framework-compare/kernel-recheck-2026-11-02/bun/results.json.gz
```

这两个命令只输出统计；主表使用同一分析器的 `compare()`。其可选 Markdown 渲染器沿用历史三轮说明，不用于本次六轮报告。

重复测量沿用 [REMOTE.md](../REMOTE.md)，先在本地构建并单独编译 Kernel，将 `BENCH_KERNEL_DIST` 和经校验的 `BENCH_NATIVE_CLIENT` 交给 `pack-remote.mjs`，为新包准备同版本 Linux 运行时。使用独立、带限额的 systemd service，设置 `BENCH_FRAMEWORKS=kernel,kernel-regexp,keala`、`BENCH_ROUNDS=6`、`BENCH_CPU_PERIODS_US=10000`；两个阶段分别设置 `BENCH_RUNTIMES=node` 和 `BENCH_RUNTIMES=bun`。保持 [plan.json](plan.json) 中其余参数和 CPU 亲和性，试跑通过后再正式计量，结束按远端流程取回证据与清理。

`checksums.json` 包含本目录证据文件的 SHA256，以及两个未压缩原始结果的 SHA256。它不对自身和本说明文件作循环校验。
